# WuNa v2 - System Design Document

This document provides a detailed technical overview of the WuNa v2 Secure Mesh Messaging System.

## 1. System Architecture: Peer-to-Peer Mesh

WuNa v2 operates as a decentralized, peer-to-peer (P2P) mesh network. Unlike traditional client-server models, there is no central authority or server. Every node in the network, or **peer**, acts as both a client and a server.

-   **Topology:** The network topology is a **partially connected mesh**. Peers are not necessarily connected to every other peer. Instead, they form a dynamic web of connections, and messages are relayed through this web to achieve network-wide propagation.
-   **Resilience:** This decentralized model eliminates single points of failure. The network can continue to operate even if some peers go offline, as long as a path of connected peers exists between any two nodes.

## 2. Peer Discovery: UDP Broadcasting

To facilitate the dynamic creation of the mesh, peers need a way to find each other on the local network automatically.

-   **Mechanism:** WuNa uses **UDP broadcasting** for peer discovery.
    -   **Broadcasting:** A dedicated thread on each peer periodically (every 10 seconds) sends a UDP broadcast packet to a specific port (`12345`). This packet contains the peer's own IP address and TCP listening port. The broadcast is sent to the network's broadcast address (`<broadcast>`), ensuring it reaches all devices on the same subnet.
    -   **Listening:** A second dedicated thread continuously listens on the same UDP port for broadcast packets from other peers.
-   **Connection Initiation:** When a listener thread receives a broadcast from a new, unknown peer, it initiates a TCP connection to the IP and port specified in the packet. This process dynamically builds the mesh.
-   **Self-Connection Avoidance:** Peers will ignore their own broadcast packets to prevent attempts to connect to themselves.

## 3. Network Communication: TCP Connections

Once peers are discovered, all subsequent communication, including message exchange, is handled via persistent **TCP connections**.

-   **Peer Lifecycle:**
    1.  **Listening:** Upon startup, each peer opens a TCP server socket and listens for incoming connections on its specified port (e.g., `8000`).
    2.  **Connection Handling:** Each new incoming TCP connection is handled in a separate thread. This allows a peer to manage connections with multiple other peers simultaneously.
    3.  **Connection Set:** Each peer maintains a `set` of its active TCP connections. This set is used for broadcasting and relaying messages.
    4.  **Disconnection:** If a TCP connection is lost (e.g., a peer goes offline), the connection is removed from the active set.

## 4. Message Propagation: Controlled Flooding

To ensure a message reaches all peers in the network, WuNa employs a **controlled flooding** algorithm.

-   **Mechanism:** When a peer receives a message (either generated by its user or relayed from another peer), it forwards that message to **all** of its connected peers, except for the one it received the message from.
-   **Duplicate Prevention:** A pure flooding algorithm would result in an infinite loop of messages. To prevent this, WuNa uses a **unique message ID (UUID)** system.
    -   Every message is assigned a UUID upon creation.
    -   Each peer maintains a `set` of `seen_message_ids` for messages it has recently processed.
    -   Before processing or relaying any message, a peer checks if the message's ID is in its `seen_message_ids` set. If it is, the message is discarded as a duplicate. If not, the ID is added to the set, and the message is processed and relayed.

## 5. Security & Authentication Model

Security is a core component of the system, based on public-key cryptography.

-   **Peer Identity:**
    -   Each peer is identified by a unique, persistent **2048-bit RSA key pair**.
    -   These keys are generated on the first run and stored locally in the `keys/` directory. The public key serves as the peer's verifiable "address" or identifier.
-   **Authentication and Integrity:**
    -   **Digital Signatures:** Every message sent is digitally signed with the sender's private RSA key. The signature is attached to the message.
    -   **Verification:** When a peer receives a message, it uses the sender's public key (included in the message) to verify the signature.
    -   **Trust Model:** If the signature is valid, the message is considered authentic (it truly came from the claimed sender) and has its integrity intact (it was not tampered with in transit). If verification fails, the message is discarded.

## 6. Offline Collaboration Features

WuNa is designed to be resilient and support asynchronous communication.

-   **Persistence Layer:** A local **SQLite database (`chat_history.db`)** is used for all persistence.
-   **Message History:** Every validated message a peer receives (including its own) is saved to the `messages` table in the database. This provides a persistent, chronological history of the chat, which is loaded on startup.
-   **Offline Message Queuing:**
    -   If a user sends a message while not connected to any other peers, the message is not discarded.
    -   Instead, it is saved to a separate `outgoing_queue` table in the SQLite database.
-   **Automatic Synchronization:**
    -   When a peer successfully establishes a new connection with another peer, it immediately checks its `outgoing_queue`.
    -   If there are any queued messages, it broadcasts them to the network.
    -   Once broadcast, the queue is cleared. This ensures that offline messages are delivered as soon as the peer rejoins the mesh.
